# Compute Execution Layer

## Responsibility

This repository implements server-side entity and JPL execution, DynamoDB-backed platform operations, capability discovery/build/registry/edit/diagnosis, protected-asset brokering and audit, provider calls, background model responses, relationship modules, indexing, and other server capabilities.

It is the server execution and persistence layer, not the owner of browser-local semantics. Data-defined local semantic entities that describe ContextDB row operations belong to `aws`; they are not remote Compute applications and must not be promoted into JPL merely because a Path was missing.

## Owns

- Entity retrieval, versioning, execution, and server persistence
- JPL runtime semantics, schemas, validation, and safe module availability
- Parent/child lineage execution mechanics and relationship operations
- General `map`, `extend`, `link`, `use`, and `substitute` mechanics
- Capability manifests, entity plans, registries, generation, editing, diagnosis, and typed output validation
- Contract-based capability reuse, compatible repair/versioning, fork/lineage decisions, installation references, and promotion/deprecation lifecycle
- Provider request execution and sanitized provider diagnostics
- Trusted-server protected-asset storage, consent enforcement, scoped resolution, use, and audit
- Durable model/build/repair jobs and idempotent application
- Server-side authorization enforcement
- Fail-closed authorization and environment scoping for destructive test operations
- Scheduled task persistence, EventBridge invocation, and due-occurrence execution
- Account/email-verification records and public device-key/authenticator registration
- Streaming presence, invitations, scoped session credentials, and channel lifecycle
- SES email delivery, consent, rate/reputation safeguards, suppression, and bounce events
- Idempotent publication, versioning, linking, authorization, and hydration of ordinary local entities and hard-data facts
- Recipient/device protected-asset grants, envelope retrieval, key-version lifecycle, and zero-trust sharing metadata
- Durable authenticated notifications, browser acknowledgement, lifecycle resolution, and privacy-safe email fallback
- Sanitized model usage traces for discovery, generation, interpretation, diagnosis, and verification responses
- Trusted resolution of versioned LLM template IDs for compute discovery, generation, interpretation, diagnosis, and verification

## Does not own

- Browser-local Path signature matching
- Ordinary local ContextDB question routing
- Primary classification and execution of ordinary local fact, event, delta, relationship, and correction mutations
- Browser persistence and refresh lifecycle
- The public CORS/proxy contract
- A claim of zero-knowledge when server code can resolve plaintext

## Entity and JPL generation

Generators must receive the authoritative schema, allowed modules, runtime reference syntax, protected-asset rules, current entity and manifest when editing, linked semantic evidence, and validation feedback. They should return structured patches or schema-bound documents rather than JSON embedded in prose. A generated one-slot EntityPlan response that uses a different label for the sole type-compatible declared output is reconciled to the contract's output identity; multi-output, incompatible, missing, and ambiguous mappings still fail closed.

An explicit fixed from-to transition that survives in Convert requirements cannot disappear because discovery omitted its effect. Deterministic normalization synthesizes `contextdb.replace_object` only when the selected operation has exactly one eligible required utterance string input; an ambiguous or otherwise unsatisfied mutation requirement rejects the build. Existing-capability reuse is held to the same authored contract: the selected operation must already contain the exact transition effect, derived response family, and every explicitly declared invocation example. A positioned capability that is merely similar fails with `CAPABILITY_REQUIREMENT_MISMATCH`, giving the bounded discovery correction a chance to select or build a compatible entity. Ordinary read-only value conversions are not mutation requirements.

The v1 Convert authoring envelope may supply ordered `requirementSegments` plus a separate bounded `authoringContext`. Compute validates up to 20 ordinary recent-input summaries and 120 four-cell browser-proven Essence rows; `relevantItems` remains empty. When a bounded requirement explicitly declares what the user will ask, say, type, enter, or request, Compute deterministically retains that clause as an utterance example on the selected operation instead of allowing a discovery paraphrase to replace it. Discovery is semantic-first: a build response declares a structured answer plan before its capability request, and Compute reconciles the operation/input/output plus any ContextDB subject/property address against that plan before executable generation. An explicitly requested state-changing operation may declare bounded `contextEffects`; `contextdb.replace_object` names a required utterance entity-reference input plus fixed current and new scalar graph values. Response outputs stay separate from the graph replacement value. Such a manifest must be non-read-only and non-cached. Compute validates and fingerprints the effect but never receives or mutates the browser graph; JPL returns the typed response output and the browser remains the mutation authority. A matching ordinary authoring value may prove that a ContextDB address exists or the declared effect precondition, but it cannot become an undeclared default, capability identity, or provider literal. Generated current-user aliases normalize to canonical `speaker`; the deictic owner is binding-address metadata rather than an ordinary value. Generated discovery may repair an undeclared owner-as-utterance-value into the planned ContextDB property input, including discarding a copied current value when the requirements themselves identify the same current-speaker property; it canonicalizes an owner-named ContextDB input to its non-deictic property name or merges an identical property binding, strips a redundant deictic prefix fused into that speaker-owned property when the remaining identifier exactly matches its generated input, and EntityPlan augmentation cannot re-add a redundant current-speaker pseudo-input. An explicitly declared property, explicitly declared input name, or non-deictic person example remains untouched. Convert authoring cannot return `not_compute` merely because runtime data resolves locally. Background discovery gets one validation-informed semantic correction; a second invalid result fails closed. Every normalized operation carries a nonempty answer template so Compute acceptance and browser Path validation agree. Matching hard-stop invocation and response families own the exact quoted response wording and punctuation even when model-authored examples omit annotations or use multiword subject variants. A continuation polling the exact build it started returns `BUILT_AND_REGISTERED`, not `CAPABILITY_REUSED`, and retains a bounded typed copy of that build's ArrayLogic, Shorthand, and JPL inspection artifacts; genuine discovery of a pre-existing definition remains `CAPABILITY_REUSED`. Browser compilation and acknowledgement remain the Path-signature authority. See [decisions 0038](../../architecture/decisions/0038-convert-hard-stops-compose-requirements.md), [0044](../../architecture/decisions/0044-semantic-answer-plans-precede-compute-contracts.md), [0045](../../architecture/decisions/0045-convert-discovery-receives-bounded-ordinary-authoring-context.md), and [0046](../../architecture/decisions/0046-browser-applied-compute-context-effects.md).

Validated manifests derive one logical `entityDependency` for each ordinary ContextDB effect. Its identity includes the exact Compute entity ID, version, operation ID, and effect index; `current_state` is only a readable label. For cross-user reuse discovery, semantic evidence may additionally contain the current utterance, at most 20 recent ordinary inputs, and no more than 200 browser-selected ordinary entities with bounded relations among them. The model selects the semantic Compute operation. When one browser-resolved invocation subject plus that operation's declared current/result transition identifies exactly one supplied relation per dependency, Compute derives the exact dependency, property, subject, and relation IDs without asking the model to copy opaque identifiers. Otherwise the model may return `entityUseBindings`, but deterministic validation accepts only IDs from the selected operation and supplied evidence; the relation property/subject cells and current/result object value must agree, and the resolved invocation entity constrains the target subject. Missing, duplicate, invented, wrong-operation, wrong-subject, wrong-value, and ambiguous bindings fail closed. Protected evidence is outside this contract. The accepted binding returns with `CAPABILITY_REUSED`; the browser owns Path compilation, persistence, mutation, and ID-remap application. See [decision 0048](../../architecture/decisions/0048-compute-installations-bind-entity-use-by-exact-id.md).

When a fixed ContextDB replacement already declares its new scalar result, a model-generated answer plan cannot reinterpret that effect's utterance-bound subject as ContextDB answer data. Compute deterministically restores the answer source to the declared literal transition result while preserving unrelated ContextDB answer inputs. If generation annotates the fixed current or result value as an additional required utterance input even though that value does not occur in its invocation example, normalization removes the invented input before Entity Plan generation; a transition value actually spoken by the user remains an ordinary input. For a declared one-slot effect command family, the same repair removes unused model-invented optional utterance inputs as well as required ones; an input explicitly named as an input, parameter, or argument remains.

After discovery, a one-input/one-output type-compatible local projection is a deterministic compiler case, as are exact-name projections and declared arithmetic. It skips background implementation generation, emits only trusted response JPL, and still passes required-input/output validation. Unmatched multi-input transforms and external or protected work remain schema-bound EntityPlan generation. See [decision 0042](../../architecture/decisions/0042-local-data-jurisdiction-and-opt-in-compute-caching.md).

A completed creation response exposes `convertArtifacts` v1: the accepted ArrayLogic, the exact Shorthand rows compiled by `parseArrayLogic`, and the materialized entity JPL limited to `published.modules` and `published.actions`. This inspection contract mirrors validated build artifacts already returned through legacy fields; it does not include prompts, hidden reasoning, protected plaintext, request headers, or runtime context. Pending and reuse responses retain the shape with null artifacts.

Compute capability reuse does not treat a model-generated `capabilityIdHint` as a universal signature. Registry writes derive an exact SHA-256 contract fingerprint plus signature-bundle-v3 semantic documents: one sanitized full contract and bounded generalized command-pattern projections. Pattern extraction uses placeholders such as `wash my {vehicle}`; the independently embedded command projection renders the declared input name as ordinary words (`wash my vehicle`) and excludes capability labels and generated descriptions. Raw example values, protected values, defaults, and answer prose are excluded. Position indexes every projection, capability discovery uses a bounded 512-band candidate window and top-K cap, and the registry reloads current manifests and explicit `use` grants before discovery may select reuse. The command projection avoids requiring a short request to occupy the full contract embedding's anchor neighborhood; the wider capability-specific window still does not permit a table scan. Public visibility permits discovery/read only; Convert-created reusable public compute definitions carry a separate canonical `pub` use grant. Reuse returns the exact manifest; it never loads the creator's Path or local bindings. Existing definitions require v3 backfill before this path can find them at catalog scale. See [decision 0039](../../architecture/decisions/0039-compute-contract-fingerprints-and-positioning.md) and [decision 0048](../../architecture/decisions/0048-compute-installations-bind-entity-use-by-exact-id.md).

For a qualified invocation such as “Austin's register status report,” discovery separates the concrete referent from the capability query. Search receives “register status report”; bounded model evidence labels Austin as invocation data. When the browser has resolved the ordinary referent locally, its exact entity ID may accompany the evidence solely to constrain this caller's Path-scoped referent or entity-use binding; it never enters the shared manifest, fingerprint, or Position. An identity-scoped browser Path may persist that ID in bounded `referentMemory` and apply it to a ContextDB subject, while the shared capability remains owner-independent. Path persistence validates the memory shape and affected input names. Named hydration may accept one remembered `usr_…` ID only after the current public profile record proves that exact ID still owns the same normalized label; otherwise ordinary candidate resolution resumes. See [decision 0041](../../architecture/decisions/0041-path-scoped-referent-memory.md) and [decision 0048](../../architecture/decisions/0048-compute-installations-bind-entity-use-by-exact-id.md).

Generation is the last capability option, not the generic fallback for every Path miss. Compute must reject or return local-routing diagnostics when validated evidence identifies an ordinary graph operation. An exact compatible contract is reused across callers with separate bindings and installations. A defect may revise implementation only while its semantic contract remains unchanged; a contract delta in inputs, outputs, operations, effects, guarantees, or trust requirements must create a fork/child or new root rather than silently edit the source.

Bulk Path persistence validates every submitted Path before writing any member of the batch. A validation failure returns the rejected signatures with zero writes; callers must never interpret a partially accepted foundation dataset as complete. Its structural schema accepts browser-owned Pattern Schema v3 and v4 envelopes plus the vocabulary-neutral `entity_list` slot used to persist repeated typed roles. Conditional Essence rows may use positive `whenAll`/`whenAny` guards or a negative `whenNone` guard; every referenced binding must be declared, and an item with no guard is rejected consistently by browser and server. For v4, Compute validates the signature namespace, bounded ordered subpattern references, complete-coverage declaration, slots, transform, tests, and quality evidence; it does not activate subpatterns or interpret the browser-local composition.

The optional Path creator-audit index key is written only when the authenticated cookie supplies a nonempty creator identity. Identity-scoped Path ownership continues to use the separately resolved target identity; persistence must not invent an audit actor or send an empty secondary-index key when creator metadata is unavailable.

Path-family normalization must preserve browser-validated exact aliases. Derived numeric answer operations such as sum, subtraction, division, and count are all quantity-answer contracts for alias compatibility; persistence must not discard an installed wording merely because its canonical query expresses the answer through an arithmetic operator.

Reviewed Path foundation promotion is distinct from identity-scoped Path persistence. Compute accepts only an authenticated, explicitly authorized confirmation of an exact Path carrying an originating sentence plus passing browser-test or dataset-quality evidence. It stores that artifact and promotion provenance in the retained `PathFoundationTable`. Listing the shared foundation is read-only hydration; browser-local compilation and testing remain the semantic authority.

Validation should cover:

1. JSON syntax and schema
2. Forbidden keys and unsafe references
3. Module/action availability
4. Input consumption and output production
5. Provider host and parameter policy
6. Protected-asset requirements
7. Manifest/JPL/template semantic alignment
8. Isolated runtime result against fixtures

## Provider protocols

Provider knowledge belongs in reusable versioned entities or protocol lineages. The core runtime supplies generic HTTP, transformation, credential-reference, validation, and diagnostic mechanics. A provider entity supplies endpoints, parameter definitions, response mappings, versions, and provider-specific normalization.

Discovery accepts only values grounded in the utterance. For a typed date resolver, one explicit relative-day surface such as “today” is the grounded value even if the model returned its normalized ISO equivalent; Compute restores the spoken surface before browser replay. This narrow semantic equivalence does not permit normalization of locations, credentials, remembered context, or other fields.

Validated compute entities may also use the allow-listed, side-effect-free binary arithmetic target supplied by the JPL runtime. This supports reusable local transforms without inventing a provider call or admitting arbitrary modules or JavaScript.

Entity Plans may contain zero provider requests when an operation only transforms or presents ordinary inputs that the browser has already resolved. A binding hint such as `contextdb`, `utterance`, `environment`, or `default` describes browser input resolution; it is never a provider address and must not create a server fetch. The compiler emits only the trusted response action for this case and omits the unused Axios module and host allow-list entries. Initial background generation may use provider research when needed, but it is not forced for input-only plans. See [decision 0040](../../architecture/decisions/0040-browser-resolved-inputs-are-not-providers.md).

An operation may declare that transform as a typed two-operand `calculation` contract. Compute deterministically compiles its operator and input/literal operands into trusted Math JPL, so deterministic arithmetic does not need an external provider and cannot bake utterance example values into the implementation.

Entity Plans may bind a later request parameter to a path in an earlier provider response from the same ordered operation. This is the generic discovery-then-detail primitive needed for flows such as place lookup followed by current conditions; the compiler rejects future request references. Provider credentials remain Protected Asset requirements rather than ordinary inputs.

An ordinary input referenced by an EntityPlan provider request is execution-required unless it has a non-null default. Provider research may promote an existing optional input to required while preserving its type and binding contract. The compiler and legacy declarative-action validator reject optional unresolved provider placeholders, and implementation policy 12 forces older entities to rebuild under this invariant.

Protected request fields use canonical `query`, `header`, or `body` injection locations. Bounded generator aliases such as “query parameter” are normalized at the protected-contract boundary, while the stored requirement, entity data, and declarative provider placeholder remain synchronized.

During an authorized entity revision, a missing requirement-field copy may be reconstructed only from its exact `{|protected=>requirement.field|}` placeholder and literal request container/parameter in declarative JPL. Compute mirrors that non-secret metadata into the entity and manifest before ordinary protected-contract and implementation validation; it cannot infer a credential value or a new destination.

If the revision instead leaves exactly one provider request placeholder as an undeclared ordinary input and exactly one Protected Asset requirement is incomplete, Compute moves that single placeholder into the protected namespace and derives the field metadata from its literal injection point. Multiple requirements or multiple undeclared request fields remain ambiguous and fail validation.

Background construction may research primary provider documentation through bounded OpenAI web search when an external provider is required. Input-only plans do not require research. If deterministic validation rejects a plan that named real public hosts, the next bounded correction restricts search to those provider domains. Researched output still has no authority until the ordinary EntityPlan compiler, host policy, protected-field checks, and output validation pass.

Background discovery failures cross the relay as a sanitized application-error contract containing code, stage, retryability, safe provider status, and message. HTTP 200 from the relay does not turn that nested failure into success. Terminal build envelopes carry the same retryability signal for transient 429, 503, timeout, and connection failures. These failures may authorize a bounded replacement job in the browser; configuration, authorization, malformed-job identity, and deterministic validation failures remain non-retryable.

This preserves the long-term direction in which providers or builders can publish their protocol work through 1var rather than requiring every end-user entity to rediscover an API.

## Distributed entities

Compute exposes one canonical persistence port at `app/persistence/canonicalPersistence.js`. It isolates physical Words, entities, subdomains, groups, links, versions, legacy access/verification, grants, identity support, the Context compatibility sidecar, sharded canonical projections, and Position/Search postings. Shared entity getters, active Context persistence, Position, and retrieval access use this port while keeping existing public response envelopes. New canonical-family modules should use the port rather than importing table names or compact legacy attributes.

New Context publication compiles deterministic counter-free Word, entity, address, Context group/head, relation, version, grant, mapping, profile, and audience records before writing the sidecar. `CanonicalProjectionTable` contains rebuildable sharded indexes only. Context hydration dual-reads canonical plus sidecar records, selects the highest record version while canonical wins an equal-version tie, and reloads grants. This prevents an eventually visible older canonical foundation row from hiding an immediately consistent newer sidecar revision. This is an implementation foundation, not a cutover claim: historical backfill, all legacy creator migration, broader typed queries, and sidecar retirement remain incomplete.

New Position postings use `AB2` partition-key shards and carry canonical revision/content evidence. Compute manifest registration writes an exact contract hash plus a sanitized semantic Position, with tenant postings for the owner and global postings only for public definitions. Search reads v2 plus legacy v1 candidates through a bounded, configurable band window (160 by default; 512 for capability-candidate retrieval), reloads current subdomain records, derives visibility from server state, distinguishes read visibility from an explicit `use` grant, authorizes the caller, and only then ranks. Stale-posting deletion, existing-definition backfill, exact reranking, and deployed scale/cost gates remain work. Retrieval projections cannot supply identity, facts, or authorization.

## Entity middleware, composition, and governance

`app/entityComposition.js` is the mechanical source of truth for `map`, `extend`, `link`, `use`, and `substitute`. Only owning `extend` edges participate in ordinary middleware ancestry. Root-to-target lineage must be unique, bounded, and acyclic. `app/entityMiddleware.js` runs that lineage sequentially, re-authorizes `use` per node, and terminates on the first validated `respond` or `fail`; it does not imply retry or execution-plane authority. Legacy `execute` authorization is normalized to `use` at the governance boundary.

The active `map`, `extend`, `link`, `useGroup`, and `substituteGroup` routes preserve their legacy response and field writes while calling `canonicalComposition` for endpoint authorization and typed relation/version/audit conformance. Exact `verifyThis` evidence is accepted only for the same legacy resource/action while older records lack canonical ownership/grants. Do not broaden that adapter or infer authority from relationship membership.

`app/governance.js` owns the canonical action and lifecycle decision. `canonicalLifecycle` writes state, immutable version evidence, and an allow-listed audit event through one conditional transaction. Entity invocation authorization loads the target address and entity with consistent foundation reads so an acknowledged create can be used immediately instead of depending on eventual-consistency timing. `CanonicalAuditTable` is retained, encrypted, and sharded by resource/month/event; no arbitrary request, response, prompt, or protected value belongs there. Protected Asset broker authorization, wrapping, consent, and revocation remain additional checks. See [the cross-layer contract](../../architecture/docs/entity-middleware-composition-and-governance.md) and [decision 0027](../../architecture/decisions/0027-versioned-entity-middleware-composition-and-governance.md).

Entity middleware remains distinct from the phase-10 execution transport. Manifest-backed `runEntity` now accepts and returns execution-envelope v1 for the `compute-jpl` plane and reports its governed entity execution effect; it is still not permitted to execute additional ancestors merely because the middleware library exists. The execution adapter canonicalizes a public `runEntity/<entity>` action to the internal `/cookies/runEntity/<entity>` route before legacy middleware resolution, while preserving the authenticated cookie and governed entity target. Browser-main, `fileWorker`, and Compute/JPL keep separate trust and effect authority.

Compute discovery also emits intent-jurisdiction v1. Existing exact contracts produce reuse, failures inside an existing operation produce repair, an added operation produces fork, and no compatible contract produces build. A post-local-proof request carries only bounded failure interpretation as untrusted jurisdiction evidence, so an external request is not forced back into a local query contract. Cross-owner registry candidates require an active canonical `use` grant and execution authorizes again; local Paths, ordinary bindings, and Protected Assets are not shared with the definition. The legacy `extend` field remains during client migration, but cannot erase the typed evolution outcome. Indexed candidate retrieval is an implementation foundation for new/edited manifests; existing-definition backfill, immutable compatible releases, persisted fork lineage, first-class user installations, exact reranking, promotion, and dependency-range enforcement remain incomplete.

Compute capabilities are one entity subtype. The server also persists hard data, structure, interaction assets, and reusable entity content. A browser publication request must create or resolve typed nodes and relations idempotently, return authoritative IDs/versions, preserve provenance and ownership, and apply public/private plus action-level authorization. Cross-user graph queries must be scoped by the caller's grants; creator identifiers are not authorization tokens.

The active Context graph v1 actions verify that the path-selected workspace belongs to the authenticated principal. The current speaker maps to a stable principal node; other people resolve only by exact unique public handles. Compute derives connected-component audiences from those resolved identities, stores one versioned node/relation view per participant audience, and returns stable IDs in the acknowledgement. Ordinary hydration queries only `u:<authenticated principal>`, never a client-selected audience. For a public workspace, only components connected to that principal's current-speaker node also receive `public:<principal>`. An executed current-speaker name-property assertion registers an exact profile; named hydration accepts a label, exact-resolves one public profile, and selects that profile's public partition server-side. Removed relations are tombstoned for current and former audiences, and records retain publisher/source provenance. The retained encrypted `ContextGraphTable` is separate from legacy creator exports and protected-asset storage. See [decision 0021](../../architecture/decisions/0021-participant-scoped-context-publication.md) and [decision 0022](../../architecture/decisions/0022-public-profile-named-context-hydration.md).

A previously persisted principal-local Context node mapping may be reused only when its canonical node is semantically compatible with the submitted node. Incompatible reuse returns `CONTEXT_LOCAL_ID_REUSED` without modifying the prior node. A same-ID relation whose subject, predicate, object, or metadata changed is a new relation version rather than an idempotent no-op.

## Recipient-specific protected sharing

The server stores opaque content ciphertext and per-recipient/device wraps created locally. A separate principal-first record grants canonical `use` with `provider` or `recipient` delivery. Provider-only use can inject plaintext only inside a destination-bound Compute request; it cannot return an envelope or grant edit/delete/delegate. Recipient retrieval returns only that principal's wrap. Both paths require the current asset version. Executor/KMS wraps remain a separate trusted-server option. Membership changes, key rotation, recipient removal, and future-version confidentiality still require explicit rewrap or re-encryption lifecycle operations.

Protected policy now also declares `trustMode` and `plaintextRetention: never`. Local-zero-knowledge envelopes are rejected if they contain an executor wrap, and the broker returns `LOCAL_EXECUTION_REQUIRED` before KMS decryption. Trusted-server provider-use envelopes require an executor wrap; `every_use` and `preapproved` distinguish options 2 and 3. Owner policy changes arrive as a new browser-encrypted envelope plus normalized metadata in one conditional version rotation; no plaintext enters this route.

Context publication may carry a protected-value placeholder only as the generic `protected_asset` node plus an opaque reference. Compute resolves the reference to the Protected Asset table and rejects it unless the active asset belongs to the authenticated publisher. The reference is retained in canonical and sidecar node records and returned by authorized hydration so a browser can request access. It is not a grant, wrap, value, or server-decryption permission; plaintext and aliases remain forbidden from Context records.

The legacy passphrase route remains ciphertext-only compatibility. Its useful exchange is now carried by Protected Assets: recipients publish public encryption keys, the sender creates a fresh salt and wrap locally, and the server stores the salt, ephemeral public key, IV, ciphertext, and explicit grant without plaintext.

When a recipient lacks `use`, the server can persist an opaque access request and notify the owner. Approval is not a notification effect: the owner browser unwraps the existing content key and supplies a wrap for the requester's current account public key plus a selected one-use, 15-minute, 1-hour, 1-day, or permanent grant window. Compute atomically stores that wrap, the lifecycle-bound versioned recipient-delivery `use` grant, and the decision. Recipient-envelope reads reject expired or exhausted grants and consume a one-use grant atomically. A retryable, idempotent publication then confirms only the opaque reference, decision, and lifecycle to the requester.

The generic notification inbox distinguishes browser acknowledgement from governance resolution. Publications schedule a one-minute SQS fallback; a browser acknowledgement suppresses email and clears the per-principal reminder latch but leaves unresolved work in the inbox. Only a decision or explicit dismissal resolves it. Verified notification contacts are stored separately as KMS ciphertext and decrypted only at the SES send boundary. Email contains no protected reference, request details, or decision.

## Canonical migration proof

`app/persistence/canonicalMigration.js` replays one bounded sidecar audience page at a time, compares identity-bearing graph fields, and blocks canonical-only cutover until backfill, zero-mismatch parity, scale, security, and rollback evidence all pass. `canonicalScaleProof.js` measures sample size, p95 latency, fan-out, partition skew, cross-principal/protected leakage, compatibility regressions, and unclassified failures. These are deployment gates, not claims that production backfill or load testing has already completed.

## Background lifecycle

Entity creation and repair may outlive a Lambda request. Jobs require stable identity, owner and authorization scope, original request hash, phase/state, model response handle, retry count, checkpointed artifacts, terminal result, expiration, and idempotent application. SQS or another durable trigger can continue work; the website polls status through fresh requests.

If an entity-revision submission response is lost, repeating the identical revision reconnects to the stored job with the same request hash. A different revision still receives the active-edit conflict and cannot adopt another request's model work.

Typed revision patches keep array replacement strict. For object members, `add` and a generated `replace` of a missing member converge to the same assignment before the complete revised entity, manifest, JPL, protected contract, and semantic synchronization gates run.

Generated Protected Asset requirement, provider, and field labels are canonicalized into stable identifiers before those gates, and exact declarative protected placeholders are rewritten with the same mapping. This accepts harmless model formatting such as spaces without weakening the strict persisted contract or changing an injection destination.

When one incomplete requirement and one credential-like ordinary request input are unambiguous, revision validation moves that input into the protected namespace, removes it from utterance examples, and derives the field's existing literal request destination. Competing inputs or destinations remain ambiguous and fail closed.

If a protected placeholder occurs in exactly one literal declarative provider host, missing non-secret provider metadata is derived from that host before validation. Multiple hosts remain ambiguous; no protected value is inspected or inferred.

An official-provider repair may receive up to three bounded validation continuations after its single research pass. Each continuation receives only deterministic failure feedback and the already-approved evidence; it cannot repeat research or bypass validation.

Completed capability output uses a short single-finalizer lease before Shorthand materialization and registry publication. Overlapping Lambda polls remain pending, a lost holder may be replaced after expiry, and only the holder may commit terminal state. A poll carrying the same validated build ID, owner, capability ID, and request hash reconnects to that build before catalog collision checks; its own newly registered entity therefore cannot be mislabeled as a competing definition. A fresh unrelated collision remains fail-closed and requires compatible reuse or explicit Edit. Failed state retains a bounded code and sanitized message for later polls. Approved child-capability Shorthand uses an empty published seed when the optional parent workspace document is unavailable; it still creates and saves the child through ordinary entity routes. See [decision 0031](../../architecture/decisions/0031-lease-compute-build-finalization.md).

Generated entity/app Shorthand reads registered-route results through `ROUTEGET`, which unwraps direct and relayed transport envelopes before selecting a named field. Ordinary `GET` remains exact object traversal; compilers must not encode one historical router wrapper depth into new entity-creation plans.

When Convert creates a compute entity, it also writes the creator's canonical action grant for the newly returned entity address before reporting the manifest ready. Creation must not return an entity that its creator cannot immediately `use`; the grant is scoped to an entity proven to be in that request's `createdEntities` result. If that newly created compute address is public, Convert separately writes a canonical `pub` grant limited to `find`, `read`, `aggregate`, and `use`. Visibility alone never supplies execution authority.

Repair and fork jobs are distinct lifecycle operations. A published repair creates an immutable compatible implementation release in the same capability lineage. A fork creates a separate identity with explicit source lineage and cannot replace or migrate dependents without a separately authorized promotion decision.

Completed model responses expose only the versioned cost-trace fields needed for local estimation: provider, model, response identity, service tier, named step, and aggregate token counts. Prompt/output content, hidden reasoning, credentials, headers, and protected values do not belong in this metadata. Polling responses must preserve one response identity so the browser can deduplicate cost.

Background model work also preserves the request's normalized `llmTemplateId`. Compute resolves the ID through a server-owned route registry; a browser value can select only a known template, never an arbitrary model or reasoning parameter. Unknown or omitted IDs use Original.

## Scheduled tasks

Time-triggered work still executes an entity through ordinary lineage, authorization, input, protected-asset, and audit rules. Each occurrence needs stable identity and idempotency. Persist the user's time zone and recurrence intent, re-check permissions at execution, and keep retry/dead-letter state observable.

## Identity, streaming, and email

Compute stores public device/authenticator material and verification state, but must not imply that credential enrollment alone authorizes a later protected operation. Streaming credentials must be short-lived and scoped to the required Kinesis channel actions. Email delivery must preserve consent, unsubscribe, suppression, rate, bounce, complaint, domain-authentication, and reputation controls for every source, including scheduled tasks and automations.

## Test-environment operations

The `resetDB` action is destructive and is never enabled merely because a caller knows its route. It fails before acquiring a DynamoDB client unless the deployment explicitly enables reset, declares an exact non-production environment identity, and the request repeats that identity. The only v1 mode is `canonical`. The normal mode requires an authenticated user allow-list. During the current disposable-stack testing phase, the explicitly configured `TEST_RESET_ALLOW_ANY_AUTHENTICATED_USER` compatibility switch temporarily allows any caller, including an anonymous portal session; the legacy name is retained to avoid changing deployment configuration. Environment, enablement, request-identity, mode, and reset-control checks fail closed. The companion client guard in `testing` prevents common operator mistakes but is not an authorization boundary. Prefer disposable test stacks or per-run namespaces as concurrency grows.

`TestResetControlTable` stores one test-environment migration marker and is never part of the deletion profile. When that marker is absent, the first canonical reset purges old authorization (`access`, `verified`), derived embedding (`embPaths`), and Context-sidecar data, then records that completed purge before clearing canonical and operational stores. A purge or marker failure blocks the canonical phase; a later canonical failure does not repeat the migration phase. Because those stores still have active compatibility writers, later canonical resets continue clearing them as compatibility cleanup until cutover. This prevents old-layout data from surviving forever without pretending it is the new persistence contract. Counter tables also remain recurring cleanup until their writers retire. The recurring profile includes grants, invitations, enabled-task state, protected assets, projections, and canonical audit evidence. Account and cookie tables are cleared last so an earlier failure normally leaves the authorized caller able to retry.

Reset execution is a durable, resumable control-table job rather than one API request. The start request only checkpoints the job. Each continuation deletes at most one 25-item DynamoDB page or resets one counter, saves an increasing step, and returns `pending` progress. A server-signed continuation authorizes only that exact environment/job after the account cookie is cleared; stale step retries return current progress without advancing twice. Missing or invalid job, token, environment, and future step values fail closed. The portal and headless client continue until `success`, with bounded retry for transient 502/503/504 responses. No request is expected to approach the API Gateway timeout.

`resetDB` clears the identity-scoped `paths` table but intentionally does not clear `PathFoundationTable`. A reset therefore removes unconfirmed learned coverage while preserving explicitly reviewed equations that every new account should hydrate. Clearing or revoking the shared foundation is a separate governed lifecycle action and is not implied by test reset.

The portal may call `resetDBStatus` to obtain the configured non-secret environment identity, canonical mode, pending legacy-purge state, and whether a resumable reset is already active, then submit that identity and mode to `resetDB` after explicit user confirmation. In allow-list mode, an authenticated but unauthorized caller receives its own account ID for administrator configuration but no environment identity. In temporary any-caller mode, anonymous callers receive the environment identity. This removes operator guesswork without weakening the server-side gates.
